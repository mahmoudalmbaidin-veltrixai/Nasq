TASK P2-06: Data versions, snapshots and freshness
PRD: §10, §17   Requirements: -   Depends on: P2-04

CONTEXT
§10: keep an input snapshot for every solve, the last synchronization marker and freshness thresholds. Newer data marks affected plans stale and notifies; it must not silently overwrite historical inputs. §17: each result comes from an immutable input and configuration snapshot.

BUILD
1. Content-addressed snapshots of all inputs used by a solve (hash over canonical JSON).
2. Synchronization markers per source.
3. Freshness thresholds read from the SoT matrix with per-organization overrides.
4. A stale-detection job that marks affected plans and emits a plan.stale event once per change.

NON-NEGOTIABLES
- Snapshots are never modified after creation.
- Events are deduplicated.
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- Publishing newer data marks affected plans stale while the snapshot hash stays the same.
- Exactly one plan.stale event per change.
- Freshness is exposed in the API for the overview screen.

OUT OF SCOPE
Alert delivery (P9-04).

HANDOFF

Open a PR whose description contains: summary, design decisions, a traceability table (task, PRD section, requirement id, test name), commands run with results, known limitations, and questions for the reviewer. Do not report the task as done if any acceptance test is missing, skipped or failing.
