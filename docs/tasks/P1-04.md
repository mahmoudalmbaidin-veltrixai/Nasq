## Build prompt for Codex

```text
You are Codex, acting as implementation engineer on the Veltrix Operations Optimization Platform monorepo.
Before writing code, read AGENTS.md, the PRD sections listed below in docs/prd/, docs/adr/ and docs/data-dictionary/. Restate the task in 5 to 10 bullets, list assumptions and open questions, propose a file-level plan, then write the acceptance tests first.

TASK P1-04: Audit trail
PRD: §6, §17, §18   Requirements: AUD01   Depends on: P1-01

CONTEXT
AUD01: who did what, when and on which version must be retained. §6: every action keeps the actor's identity.

BUILD
1. An append-only audit_events table: org_id, actor id and type (user, api key, system, support), action, resource type and id, version, change summary, request id, IP, timestamp.
2. A single audit service called inside the same database transaction as the business change.
3. Database grants that deny UPDATE and DELETE on audit_events to the application role.
4. An optional per-organization hash chain to detect tampering.
5. A query API with filters, cursor pagination and export that is permission-checked.

NON-NEGOTIABLES
- Never store secrets or full personal data in change summaries.
- If the audit write fails, the business change rolls back.
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- A registry test proves every mutating route writes an audit event (test_AUD01_*).
- The app role cannot update or delete audit rows.
- The tamper check detects a modified row when the hash chain is on.

OUT OF SCOPE
Audit screens (part of P10-02).

HANDOFF
Work on branch feat/p1-04-audit-trail. Run make lint, make typecheck and make test. Open a PR whose description contains: summary, design decisions, a traceability table (task, PRD section, requirement id, test name), commands run with results, known limitations, and questions for the reviewer. Do not report the task as done if any acceptance test is missing, skipped or failing.
```
