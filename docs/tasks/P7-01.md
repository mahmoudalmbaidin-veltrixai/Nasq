TASK P7-01: Transactional outbox, idempotency and reconciliation
PRD: §14, §18, §23   Requirements: INT01   Depends on: P6-02

CONTEXT
INT01: duplicate requests and events do not duplicate effects. §23: persist outgoing submissions in a transactional outbox linked to approval; use idempotency keys; record attempts and last success; periodic reconciliation and manual review. §18: distinguish sent, accepted, failed and executed.

BUILD
1. Outbox table written in the approval transaction.
2. Dispatcher worker with retries, exponential backoff and a dead-letter state.
3. Idempotency keys on every creation command, inbound and outbound.
4. Submission states: sent, accepted, failed, executed.
5. A connector interface with file drop, REST webhook and an ERP adapter skeleton.
6. A reconciliation job comparing external status with platform status and a manual review queue for permanent errors.

NON-NEGOTIABLES
- An HTTP 200 alone never marks a submission executed.
- Two conflicting active versions in an external system are flagged for reconciliation (§18).
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- Retry after a simulated network failure creates exactly one order in a mock ERP (test_INT01_*).
- Reconciliation flags a mismatch.
- Dead-lettered items appear in the review queue.

OUT OF SCOPE
Inventory ERP submission (P14-04).
