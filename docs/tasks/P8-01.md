You are Claude Code, acting as lead engineer on the Veltrix Operations Optimization Platform monorepo.

TASK P8-01: Explanation and infeasibility diagnosis
PRD: §16, §19   Requirements: RUN02   Depends on: P5-02, P6-03

CONTEXT
§19: distinguish facts from the plan, counterfactual diagnosis and approximate inference. When no solution exists, start with data, constraint and lock checks; give a minimal conflict where the solver supports it; proposed relaxation is a separate scenario requiring approval; never silently change a safety limit or mandatory constraint.

BUILD
1. Explanation records typed as fact, counterfactual or inference, each with evidence links to inputs, validation results or scenario ids.
2. Named pre-solve checks (data completeness, capacity versus demand, material coverage, lock conflicts) with their stated limits.
3. Infeasibility diagnosis using CP-SAT assumption literals per constraint group to obtain a sufficient set of conflicting groups; state honestly that it may not be minimal.
4. Relaxation proposals generated as separate scenarios that require approval.
5. A counterfactual runner (for example one extra shift hour) that reports the effect without claiming a sole cause.

NON-NEGOTIABLES
- Inconclusive runs are never diagnosed as infeasible.
- Safety limits and mandatory constraints are never relaxed in a proposal without an explicit flag and approval.
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- Infeasible reference cases return the correct conflicting group.
- Explanations without evidence are rejected by the API.
- A relaxation proposal never changes the active configuration version.

OUT OF SCOPE
Language assistant (P15-01).

HANDOFF

Open a PR whose description contains: summary, design decisions, a traceability table (task, PRD section, requirement id, test name), commands run with results, known limitations, and questions for the reviewer. Do not report the task as done if any acceptance test is missing, skipped or failing.
