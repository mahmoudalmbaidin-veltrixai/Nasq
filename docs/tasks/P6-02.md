```text
TASK P6-02: Concurrency-safe approval
PRD: §6, §17   Requirements: APR01   Depends on: P6-01, P4-03, P2-06

CONTEXT
APR01: changed inputs require a refresh or a recorded acknowledgment. §17: before approval check feasibility, freshness, approver authority and absence of a conflicting newer version; approval is transactional and prevents competing approved versions for the same scope.

BUILD
1. Approve, reject, request changes and revoke-before-execution endpoints.
2. Inside one transaction with a row lock on the scope: validator pass, freshness (or a recorded acknowledgment with reason), approver authority and separation of duties, no conflicting newer version.
3. A partial unique index ensuring one active approved version per organization, engine and scope.
4. Clear messages when another user already changed the record.
5. Outbox records written in the same transaction (hook for P7-01).

NON-NEGOTIABLES
- Never approve with hard violations.
- Every decision is audited with reason.
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- Stale inputs require refresh or recorded acknowledgment (test_APR01_*).
- Two parallel approvals: exactly one succeeds.
- Separation of duties enforced when enabled.

OUT OF SCOPE
Approval screen (P10-06).

HANDOFF
Work on branch feat/p6-02-concurrency-safe-approval. Run make lint, make typecheck and make test. Open a PR whose description contains: summary, design decisions, a traceability table (task, PRD section, requirement id, test name), commands run with results, known limitations, and questions for the reviewer. Do not report the task as done if any acceptance test is missing, skipped or failing.
```
