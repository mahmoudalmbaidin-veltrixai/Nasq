TASK P1-03: Authorization: role and site policy
PRD: §6, §23, §24   Requirements: IAM01   Depends on: P1-01, P1-02

CONTEXT
IAM01: a forbidden direct request is rejected on the server. §6 defines eight roles and says permissions apply to the server, imports, exports, APIs and background jobs, combining the user's role with authorized sites.

BUILD
1. docs/permissions.yaml: the permission catalog derived from the §6 table for platform_admin, org_admin, data_steward, planner, approver, execution_supervisor, finance and support.
2. A policy function authorize(actor, action, resource, site) combining role, site scope and engine entitlement.
3. A FastAPI dependency applied to every route, and a registry test that fails if any route lacks a policy.
4. Background jobs carry the actor identity and are re-authorized when they execute.
5. A separation-of-duties setting: when enabled, the author of a plan cannot approve it (§6).
6. Support access grants that are requested, approved by an org admin, limited in time and scope, revocable and logged.

NON-NEGOTIABLES
- Deny by default.
- Hiding interface controls is never the control.
- Platform admin has no default access to customer operational data (§6).
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- A permission-matrix test asserts allow or deny for every role × action × site combination.
- Direct API calls by an unauthorized role are rejected (test_IAM01_*).
- An expired support grant is rejected.
- A job whose actor lost permission fails with a clear reason.

OUT OF SCOPE
Screens for user management (P10-02).
