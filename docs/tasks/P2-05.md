## Build prompt for Codex

```text
You are Codex, acting as implementation engineer on the Veltrix Operations Optimization Platform monorepo.
Before writing code, read AGENTS.md, the PRD sections listed below in docs/prd/, docs/adr/ and docs/data-dictionary/. Restate the task in 5 to 10 bullets, list assumptions and open questions, propose a file-level plan, then write the acceptance tests first.

TASK P2-05: Validation rules and error reporting
PRD: §10   Requirements: DAT01   Depends on: P2-03

CONTEXT
§10: validate field types, units, dates, references, duplicates, plausible rates and durations, and calendar conflicts. Classify as blocking errors or warnings; report the row, field, value, issue and expected correction.

BUILD
1. A rule library with: type and required checks, known units, dates parsed in the site zone, referential integrity, duplicates, positive quantities, plausibility bounds for rates and durations (configurable), calendar conflicts.
2. Severity per rule (blocking or warning), configurable per template.
3. A report model with row, field, value, issue and expected correction, in Arabic and English.
4. Downloadable report (XLSX/CSV) using the export sanitizer from P2-07.
5. Recording of accepted warnings with reason and actor.

NON-NEGOTIABLES
- Messages tell the user how to fix the problem.
- No rule silently rewrites data.
- Organization scope comes from the session or API key only; permissions are enforced on the server; every mutating action writes an audit event.
- No secrets or personal data in code, fixtures, logs or messages. User-facing text exists in Arabic and English.

ACCEPTANCE (automated tests; name requirement tests test_<REQ-ID>_<behaviour>)
- Every rule has unit tests with valid and invalid samples.
- Report columns match §10.
- Accepted warnings are stored and audited.

OUT OF SCOPE
Screens (P10-03).

HANDOFF
Work on branch feat/p2-05-validation-rules-and-error-reporting. Run make lint, make typecheck and make test. Open a PR whose description contains: summary, design decisions, a traceability table (task, PRD section, requirement id, test name), commands run with results, known limitations, and questions for the reviewer. Do not report the task as done if any acceptance test is missing, skipped or failing.
```
